# 发布与事故响应规范

- **版本**：1.0
- **生效日期**：2026 年 9 月 8 日
- **适用对象**：所有修改 Spring Mouse 请求入口、账号路由、认证、代理、网络访问、后台任务、依赖、Dockerfile、CI/CD 或数据库迁移的变更
- **规范性质**：发布阻断标准；未满足时不得发布到生产或更新 `latest`

> 本规范将事故复盘中的建议转化为可验证要求。术语“必须”表示发布前置条件；“应当”表示默认做法，偏离时必须在发布记录中写明风险与批准人。

---

## 1. 基本原则

1. **证据先于结论**：错误文本、截图和单个测试结果只能说明观察，不等同于根因。
2. **最小变更**：事故修复只改经验证的故障点；不在同一修复中夹带重构、兼容性扩展、文档大改或无关功能。
3. **同环境验证**：CI、构建、预发布和生产必须使用同一 Node 主版本、同一 lockfile 和同一镜像构建方式。
4. **观测不得阻断业务**：流量统计、审计、日志、埋点与后台任务失败时必须降级，不能阻断主请求。
5. **可回滚优先**：生产使用已验证的不可变版本或 digest；`latest` 不是生产发布依据。
6. **敏感信息最小化**：日志、报告、测试附件和诊断脚本不得输出 Key、Token、Cookie、Authorization 或用户正文。

---

## 2. 变更风险分级

| 等级 | 变更类型 | 示例 | 发布要求 |
|---|---|---|---|
| R0 | 文案、样式、纯前端非请求展示 | Dashboard 文案 | 单元/构建检查。 |
| R1 | 单一管理 API 或局部数据展示 | 设置页字段、非关键查询 | 自动测试 + 手工 API 检查。 |
| R2 | 路由、模型列表、账号标签、数据库迁移、Provider 配置 | `getProviderCredentials`、模型可见性、迁移 | R1 + 容器级冒烟 + 审核人确认。 |
| R3 | `/v1` 入口、Request/Response 包装、认证、代理、fetch/executor、自动 Ping、依赖、Docker/CI | `networkTraffic`、`connectionProxy`、undici/Next、Dockerfile | R2 + 灰度 + 5 分钟观察 + 明确回滚方案 + 两人批准。 |

一个提交包含多个等级时，按最高等级执行。事故热修复默认至少 R2；涉及入口或网络时为 R3。

---

## 3. 不可变构建要求（发布阻断）

### 3.1 依赖与运行时

生产发布前必须满足：

- 根 `package-lock.json` 已提交且与 `package.json` 一致；
- CI 和 Docker 构建一律使用 `npm ci`，不得回退到 `npm install`；
- 根 `.gitignore` 不得忽略发布所需的 lockfile；
- Node 主版本固定，并同时用于 CI、Docker builder、Docker runner 与本地复现；
- Next、undici 等直接影响请求运行时的依赖升级必须单独提交、单独验证；
- 构建产物必须记录：Git revision、镜像 digest、Node、Next、undici、lockfile SHA-256。

任何一项缺失时：**停止发布，不允许以“本地能跑”替代。**

### 3.2 镜像与版本

- 生产 `SPRING_MOUSE_IMAGE` 必须固定到已验证的 `vX.Y.Z` 标签或 digest；
- 只在灰度验证完成后更新 `latest`；
- 版本标签必须指向唯一 Git revision；
- 发布记录必须保存旧版本、候选版本、镜像 digest 和回滚命令；
- 未经预发布验证的 commit 不得直接推送为全量生产镜像。

## 4. 测试门禁

### 4.1 所有变更

发布前必须通过：

```bash
npm ci
(cd tests && npm ci)
npm run build
(cd tests && npm exec vitest run -- --config vitest.config.js <受影响测试文件>)
git diff --check
```

测试命令必须在 CI 中以相同工作目录执行；不得只验证“依赖安装成功”。

### 4.2 R2 / R3 必测矩阵

| 场景 | R2 | R3 |
|---|---:|---:|
| 受影响单元测试 | 必须 | 必须 |
| 数据迁移升级 + 回退 | 如涉及 | 如涉及 |
| Docker production build | 建议 | 必须 |
| Node production major version | 建议 | 必须 |
| 已构建容器中的 HTTP 冒烟 | 必须 | 必须 |
| Request / Response 跨 realm | 如涉及 | 必须（如涉及网络包装） |
| 账号选择、标签、回退 | 如涉及 | 必须（如涉及路由） |
| 直连与代理路径 | 如涉及 | 必须（如涉及网络） |
| 自动 Ping / 后台任务 | 如涉及 | 必须（如涉及账号、Token、代理或 executor） |
| 真实预发布上游验证 | 建议 | 必须 |

### 4.3 上游无响应与客户端取消（所有涉及出站请求的 R2 / R3 变更）

任何新增或修改出站网络路径、代理、DNS 绕过、重试、流式转发或请求包装的 R2 / R3 变更，必须通过以下测试；仅模拟 `fetch` 返回成功不构成验收：

1. fake upstream 在 TCP/TLS 握手、响应头、首个流 chunk、流中断、非流式 body 五个阶段分别停滞；
2. 在每个停滞阶段取消客户端 Request，确认上游 `AbortSignal` 被触发；
3. 对自行持有 `net.Socket`、`http(s).request`、stream 或 dispatcher 的实现，断言 abort 会销毁底层资源并移除监听器；
4. 对 retry/backoff，断言取消后不再等待、不再发起下一次重试；
5. 在 N 个并发 no-response 请求后取消全部客户端，确认 pending requests、active sockets/handles 回到基线，新的健康请求仍能成功；
6. 记录并脱敏校验取消原因与阶段：`client_abort`、`connect_timeout`、`first_byte_timeout`、`stream_stall`、`response_body_timeout`。

超时是上游工作上限，不是资源回收的替代品：**所有**出站路径必须接受并传播同一个请求生命周期 signal。禁止 raw socket、后台 retry 或 response body reader 脱离该 signal 单独运行。

### 4.4 容器级 HTTP 冒烟

冒烟必须针对**构建后的同一镜像**执行，至少验证：

1. 容器健康检查；
2. `/v1/models` 的认证与响应；
3. `/v1/embeddings` 或 `/v1/chat/completions` 的最小有效请求；
4. 已选账号 ID、路由标签、代理状态写入脱敏诊断记录；
5. 账号测试路径 `/api/providers/[id]/test`（使用专用预发布账号）；
6. 如启用自动 Ping，运行一次受控的 scheduler tick 或等效 fake upstream 测试。

真实上游测试只能使用专用预发布账号、最小额度请求和隔离的 API Key；禁止以真实生产用户 Token 做 CI 测试。

---

### 4.5 内存、缓存与观测变更的附加门禁

- **引用链验证**：不能只看 Map 条数或 JSON 输出长度。连接池淘汰须验证资源排空，缓存 TTL 须验证不再访问时也清理，短预览须验证不会保留巨型 backing store。
- **并发首次访问**：代理/凭据缓存至少验证 100 个相同 key 的并发请求不会创建重复资源；容量检查须涵盖 `await` 后的竞态。
- **慢客户端**：dashboard 状态 SSE 必须在停止读取时保持有界并合并旧状态；不得将丢弃策略套用到聊天内容流。
- **关联链路**：移除 header 或重建 Request 前必须测试所有消费方，包括原始 headers 序列化、适配器重建和核心 usage 持久化，不可仅测 WeakMap helper。
- **隔离与归因**：测试必须使用临时 DATA_DIR、模拟凭据及假上游；旧测试失败需重现/基线对照，不得直接归为无关。模拟池创建数不是实际 socket/RSS 证据。
- **观测异步化**：必须同时限制记录数、保留字节数及在途写入数；不得以 timeout + 无限新增后台任务绕过慢 DB。必须说明是否会丢观测数据，不得将同样的丢弃策略用于计费/配额记录。
- **刷新事务边界**：deadline 必须传到底层传输并覆盖 body；成功轮换 token 后的可选元信息查询失败不得丢弃新 token。测试须覆盖共享锁释放、迟到结果及正常刷新兼容性。
- **发布边界**：定向测试通过不替代 R3 容器构建、真实上游灰度和长请求取消后的 RSS/句柄回落验证。

## 5. R3 发布流程

### 5.1 发布前清单

发布负责人必须在发布记录中逐项确认：

- [ ] 风险等级已判定；
- [ ] 变更范围与非目标范围已写明；
- [ ] 旧版本和回滚版本已验证可拉取；
- [ ] lockfile、Node、镜像 digest、依赖版本已记录；
- [ ] 单元、构建、容器级冒烟均通过；
- [ ] 预发布上游请求与代理路径通过；
- [ ] 监控面板、日志入口和回滚权限可用；
- [ ] 两名批准人已确认（代码所有者 + 发布负责人）；
- [ ] 用户影响和回滚条件已声明。

### 5.2 灰度

1. 只部署到一个实例或不超过 5% 流量；
2. 立即执行容器级 HTTP 冒烟；
3. 观察至少 5 分钟；
4. 对比灰度前后的入口 5xx、上游连接超时、认证失败、请求延迟、账号回退次数；
5. 不满足任一阈值时停止扩大，并立即回滚；
6. 指标稳定后才能逐步扩大到 25%、50%、100%。

若架构不支持按实例分流，则以单独预发布环境完成同等验证；没有预发布环境时，R3 变更不得发布。

### 5.3 回滚触发条件

出现任一条件，立即停止扩大并回滚到上一个已验证镜像：

- 新版本上线后任意核心 `/v1` 冒烟失败；
- 入口 5xx 或上游连接超时相对基线显著升高；
- 多个 Provider 同时出现不可用；
- 账号测试、自动 Ping 或真实请求出现一致的连接错误；
- 无法在 10 分钟内确认影响边界；
- 发布版本、依赖版本或镜像身份无法确认。

“先继续观察”“先热修再说”不是替代回滚的理由。应先回滚恢复服务，再在隔离环境排查。

## 6. 事故响应规范

### 6.1 首 15 分钟

1. 声明事故等级与影响范围；
2. 冻结非必要发布和非必要代码改动；
3. 固定当前证据：镜像 digest、revision、容器日志、错误样本、时间窗口；
4. 根据调用链分类：入口包装、认证、账号选择、代理、DNS/TCP/TLS、上游响应、后台任务；
5. 若影响广泛且上一个已验证版本可用，优先回滚；
6. 不得在生产上尝试未经复现的“猜测性修复”。

### 6.2 根因结论分级

| 标签 | 含义 | 报告写法 |
|---|---|---|
| 观察（O） | 截图、日志、用户反馈、指标。 | “观察到……”。 |
| 已验证事实（F） | 可重复执行、可由版本/代码/容器直接验证。 | “已验证……”。 |
| 假设（H） | 合理但尚未取证的解释。 | “待验证假设……”。 |
| 根因（RC） | 复现并能解释影响范围，且排除主要替代解释。 | “确认根因……”。 |

禁止把 O 或 H 写成 RC。错误文本相同不代表失败阶段或根因相同。

### 6.3 必须采集的脱敏证据

- 镜像 digest、Git revision、`/app/build-info.json`；
- Node、Next、undici、lockfile hash；
- 路径类型、Provider、connection ID（可散列）、路由标签、代理启用状态；
- 上游 host、错误 code、错误 cause、失败阶段、耗时、请求 ID；
- 对比基线版本的同一项数据；
- 变更列表与配置差异。

禁止采集或转存：API Key、OAuth Token、Cookie、Authorization、完整请求 body、用户 prompt、完整代理凭据。

### 6.4 事故结束与复盘

事故结束不等于问题关闭。关闭前必须：

- 已恢复服务且验证核心请求；
- 完成证据分级报告；
- 列出每项行动的负责人、截止日期、验收标准；
- 为每项 R3 行动建立可自动验证的 CI / 部署门禁；
- 在预发布环境演练一次回滚。

## 7. 请求链路可观测性要求

以下字段必须以脱敏方式关联到日志或指标：

| 阶段 | 最低字段 |
|---|---|
| API 入口 | request ID、路由、HTTP 状态、耗时、是否进入 handler、包装器错误类型。 |
| 认证与路由 | API Key ID 哈希、请求标签、候选账号数、选中 connection ID 哈希、回退次数、拒绝原因。 |
| 网络与代理 | proxy source、是否启用代理、上游 host、DNS/TCP/TLS/首字节/读取失败阶段、cause code。 |
| 账号测试与自动 Ping | connection ID 哈希、触发源、Token 刷新结果、配额查询结果、失败冷却状态。 |
| 发布身份 | image digest、revision、Node、Next、undici、lockfile hash。 |

Dashboard 的简短 `lastError` 只用于展示，不能作为事故根因证据的唯一来源。

## 9. 事故报告模板

每次 S1 / S2 事故必须复制以下结构：

```markdown
# 事故复盘：<日期> <简短标题>

- 严重级别：
- 状态：调查中 / 已缓解 / 已关闭
- 可用基线版本：
- 故障版本：
- 影响窗口（带时区）：

## 摘要
## 用户影响
## 调用链与失败边界
## 证据分级
### 已验证事实（F）
### 运行观察（O）
### 未验证假设（H）
## 时间线（仅可核实事件）
## 根因（仅在满足 RC 标准后填写）
## 缓解、回滚与验证
## 行动项（负责人 / 截止日 / 验收证据）
## 关闭条件
```

## 10. 偏离规范

任何偏离本规范的发布都必须在发布记录中说明：

- 未满足的具体条款；
- 业务原因；
- 已知风险；
- 临时补偿控制；
- 最晚补齐日期；
- 代码所有者与发布负责人的明确批准。

没有这份记录，默认视为不允许发布。
