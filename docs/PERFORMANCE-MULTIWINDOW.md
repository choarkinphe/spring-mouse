# 20 人多 Codex 窗口并发优化与验证

## 验收口径

把 20 人 × 每人 3/5 个同时工作的窗口建模为 **60/100 路 Responses 流**，而不是 20 个连接。每路请求必须收到真实 `response.output_text.delta` 和成功的 `response.completed`；HTTP 200、响应头或空 SSE 事件不算模型已经开始回答。

本轮没有降低模型推理等级，没有提前伪造首 token，没有部署或调用真实上游。下面是本地中转层实验，不是生产 SLA。

## 改动

- **账户调度一次 Redis 往返**：将逐账户 EVAL 尝试改成一次多账户 Lua 选择并预占。保留优先/用户粘性偏好，达到软阈值后分散到其他可用账户；全部满时按占用/阈值最小值分配，溢出请求也计数。
- **独立、可续租的请求占用**：ZSET 保存唯一请求 token；默认 90 秒租约，本进程每 30 秒一次批量续租。释放按 token 删除且幂等，避免旧请求结束时误减新请求；已释放租约不会被迟到的续租恢复。崩溃租约按各自时间回收，不依赖整个账户 key 过期。
- **覆盖完整生命周期**：聊天入口在刷新凭证、查询项目、发起上游请求前持有租约，直至流完成/异常/取消后释放；无需负责聊天流生命周期的模型列表和媒体凭证查询不再偷偷预占聊天槽位。
- **路由 Redis 有界等待**：独立连接，禁止离线排队和自动重放，单次连接+命令合计默认 200ms；失败后短暂退避。不可用时热读走现有数据库回退、账户选择走本进程活跃请求统计。该连接与持久用量写入连接隔离。
- **减少热读和事件开销**：同一 key 的同时 GET 合并，只合并在途读取，不增加本地 TTL，不共享可变 JSON 对象；连接快照和配置并行读取。流 watchdog 不再每个 chunk 重建定时器，且零首包时持续检查；正常结束、报错、取消均清理。
- **可观测性**：现有管理员 `/api/system/status` 增加 `concurrency`：成功账户选择耗时直方图、事件循环延迟、进程活跃/Redis 租约数量、路由 Redis 超时和错误次数。统计范围是本进程生命周期，不是全实例或最近一分钟。`routing` 不含此前的入口鉴权、模型解析或真实上游等待；事件循环采样分辨率为 20ms，不能把约 20ms 本身当成阻塞证据。

## 同条件修改前后实验

基线是 Git `7d064bc`（0.4.43），通过 `git archive` 放入隔离临时目录；没有切换或重置工作区。两组按顺序运行，没有互相争抢压测资源。Node v24.9.0，机器报告 15 个逻辑 CPU。

包含：本机 HTTP adapter → **实际生产 `/api/v1/responses` POST** → 真实鉴权/路由/协议处理 → 本机模拟上游；真实 Redis、临时 SQLite 和独立 usage-writer 进程。8 个模拟账号（每个软阈值 8），20 个独立入口 Key，32KiB 文本提示，每档连续 3 轮；模拟上游在 75ms 后发出第一段文本，约 1.2 秒持续流式输出。每档另测直连模拟上游，作为延迟底线。

不包含：Next.js custom-server/生产反向代理、TLS、实际 Codex OAuth 上游、真实账户配额/出口代理、分钟级上下文推理。模拟上游不执行推理、没有真实 token 限流；不能把它的 75ms 延迟换成生产承诺。基线/新版各自仅一次实验、每档三波，未计算统计显著性。

| 并发流 | 每组请求 | 修改前 TTFT P50 | 修改后 TTFT P50 | 修改前 TTFT P95 | 修改后 TTFT P95 | 新版完成 P95 | 新版失败 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 3 | 82.01ms | 82.97ms | 82.64ms | 83.79ms | 1305.41ms | 0 |
| 20 | 60 | 93.96ms | 93.91ms | 112.42ms | 111.82ms | 1320.36ms | 0 |
| 60 | 180 | 113.36ms | 113.33ms | 152.29ms | 144.82ms | 1361.02ms | 0 |
| 100 | 300 | 133.27ms | 140.87ms | 173.21ms | 167.10ms | 1381.91ms | 0 |

100 并发时，修改后直连模拟上游的 TTFT P95 为 89.62ms，经网关为 167.10ms；两者分位数之差仅供开销参考，不是逐请求差值的 P95。网关路径的实际上游峰值达到 100，每档结束本进程活跃租约均为 0。新版共 543 个网关请求零失败。

**短时低延迟 Redis 场景改善很小**：100 并发 TTFT P95 从 173.21ms 到 167.10ms，P50 反而从 133.27ms 到 140.87ms；100 并发三轮进程 CPU 时间从 1662ms 到 1699ms，结束时 RSS 从 407MiB 到 433MiB。实验同时包含客户端、网关和模拟上游，RSS 是档位结束快照而非峰值，不能据此推导生产网关独立内存预算。不能宣称吞吐或首包大幅提升；本轮最明确的收益是消除串行账户探测、修复占用泄漏和长流计数、控制辅助 Redis 卡顿。

## 异常验证与复现

最终代码 `npm run build`（webpack + standalone 静态资源复制）通过；使用临时 DATA_DIR，未修改生产数据库。`git diff --check` 通过。

已通过 20 个相关单测文件、86 个用例：热读合并、Redis 连接合并/超时/退避、不重放迟到命令、账户权限/排除规则、跨模块共享计数、租约生命周期、首字节卡住/定时器清理、客户端/TLS 断连、Responses 终止事件、Codex 推理和工具透传、Key 配额及用量回归。

额外真实 Redis 集成用例：
- 100 路并发原子分配，Redis 记录 100 个独立占用，8 个账户负载最大差为 1；
- 3 秒租约持续持有 4.2 秒，续租后全部仍有效，释放后 Redis 占用清零；
- 旧请求重复释放、迟到心跳不影响新请求；单独过期的崩溃 token 正确回收；
- 暂停测试专用 Redis 1 秒，20 路请求在 800ms 的测试上限内完成进程内回退，而非等 Redis 恢复（默认单操作截止为 200ms）。超时命令可能已经在服务端执行，孤立 token 最迟按租约过期回收，所以这不是严格全局并发锁。

从仓库根目录运行（需要本机 `redis-server`、已安装 Node 依赖及本机端口权限；仅使用临时库和假 Key）：

```bash
SM_REDIS_INTEGRATION=1 npm --prefix tests test -- integration/connection-leases.test.js
SM_CONCURRENCY_BENCH=1 SM_BENCH_OUTPUT=/tmp/sm-concurrency.json \
  npm --prefix tests test -- performance/multi-window.test.js
SM_CONCURRENCY_BENCH=1 SM_BENCH_PROMPT_BYTES=262144 \
  SM_BENCH_OUTPUT=/tmp/sm-concurrency-large.json \
  npm --prefix tests test -- performance/multi-window.test.js
```

压测统计的是第一段真实文本，不是 `response.created`。脚本也支持 `SM_BENCH_DELAY_MS`、`SM_BENCH_STREAM_MS`，但客户端超时目前固定 15 秒，不适合直接设置分钟级流；分钟级生产验证应另设足够超时。压测文件默认跳过，不会在普通单测中意外启动服务。

## 上线边界与检查

```dotenv
SPRING_MOUSE_CONNECTION_MAX_CONCURRENCY=16
SPRING_MOUSE_CONNECTION_SLOT_TTL_SECONDS=90
SPRING_MOUSE_ROUTING_REDIS_TIMEOUT_MS=200
```

这是默认值，不是已经测出的真实 Codex 账号容量。单连接 `providerSpecificData.maxConcurrentStreams` 和 provider strategy `maxConcurrentStreams` 可覆盖并发提示值。以实际账户限额和长上下文行为设置；**软阈值没有拒绝/排队机制，调低它不能提供硬保护**。Redis 不可用时仅本进程计数，无法保证跨进程一致；Redis 恢复后本地回退租约不迁移到 Redis。旧整数键与新 v2 租约不混用，因此滚动升级期间旧/新版本不共享占用视图，应先排空再切换，或接受过渡期仅软调度。

本轮仅为热缓存和账户调度 Redis 增加等待上限。配额读取/持久用量队列仍使用原连接；Redis 全面故障时，完整请求仍可能受这些链路影响，不能把本轮解释为全系统 Redis 故障隔离。配置仍以 SQLite 为事实源，没有异步丢弃关键配置写入，也没有增加新的权限缓存 TTL；原有 cache-aside 回填与失效一致性问题不是本轮新增机制解决的范围。

生产上线后按 20 → 60 → 100 活跃流观察入口到真实文本 P50/P95、429/5xx/断连比例、路由 P95、事件循环延迟、代理出口连接数、Redis 超时及用量写入积压。真正 Codex 会话还需要包含长推理、工具调用、取消重试与跨分钟流的持续测试。只有生产出口和账号在目标并发下也稳定，才能承诺 20 人多窗口的体验；本地模拟压测不能替代这一环。
